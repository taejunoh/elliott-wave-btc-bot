## 1. 목표와 범위

### 목표
- 모의매매로 검증한 고정 전략을 Coinbase Financial Markets(CFM) 미국 선물 `BIP`(nano Bitcoin perp-style, 0.01 BTC/계약)에서 실제로 거래한다.
- 실거래가 모의매매와 같은 판단을 따른다는 것을 구조적으로 보장하고, 그 사실을 계속 측정한다.
- 서버가 죽거나 거래소에 장애가 나도 포지션이 보호된 상태로 남게 한다.

### 비목표
- 전략, 파라미터, 리스크 프로파일 변경. 보수 프로파일만 쓴다. 공격 프로파일은 검증되지 않았다.
- 다중 거래소, 다중 상품, 동시 다중 포지션
- 웹 대시보드. 텔레그램과 HTML 리포트로 대신한다.

### 결정 사항 (2026-10-03 사용자 승인)

| 항목 | 결정 |
|---|---|
| 초기 자금 | 소액 시험(CANARY, 1계약)으로 시작하고, 기준을 충족하면 확대한다 |
| 자동화 | 승인 절차 없이 완전 자동으로 운영한다. 단계적으로 확대하고, 텔레그램 `/pause`·`/flatten`으로 언제든 개입한다 |
| 실행 위치 | 미국 동부 VPS에 상주시킨다(방식 A). 서버리스 방식(B)과 혼합 방식(C)은 기각했다. 손절 감시가 1시간 단위가 되고 API 키를 IP로 묶을 수 없기 때문이다 |
| 리스크 | 보수 프로파일(거래당 1%, 레버리지 상한 3배)만 쓴다 |

## 2. Coinbase API 사실 (2026-10-03 조사)

출처는 docs.cdp.coinbase.com, help.coinbase.com, 실제 `GET /market/products/BIP-20DEC30-CDE` 응답, CFTC 수수료 고시다. **구현 계획을 작성하기 전에 다시 확인한다.**

| 항목 | 내용 | 확인 |
|---|---|---|
| 인증 | CDP API 키로 요청마다 JWT를 서명한다(2분 만료). 알고리즘은 ECDSA를 권장한다. 권한은 `view`/`trade`/`transfer`로 나뉘고 IP 허용 목록을 걸 수 있다. `GET /key_permissions`로 권한을 확인할 수 있다 | 확인됨 |
| 상품 | `base_increment=1`(정수 계약), `price_increment=5`($5 호가 단위), `contract_size=0.01`, 펀딩 주기 3600초. 증거금률은 장중 약 0.10, 오버나이트 0.21(롱)·0.257(숏)이다 | 확인됨(실제 응답) |
| 장 운영 상태 | `fcm_trading_session_details`로 `session_state`(PRE_OPEN, OPEN, CLOSE, HALTED…)와 분기 점검 일정(`maintenance`)을 받는다 | 확인됨 |
| 주문 유형 | `market_market_ioc`, `limit_limit_gtc/gtd/fok`, `stop_limit_stop_limit_gtc/gtd`(`stop_direction`), `trigger_bracket_gtc/gtd`. **API에는 시장가 손절이 없고 `reduce_only` 필드도 없다.** TP/SL 묶음 주문은 포지션을 줄이는 방향으로만 체결된다(help center) | 확인됨 (감소 전용 동작은 도움말 기준) |
| 수정·취소·청산 | `POST /orders/edit`(선물 손절 수정 지원 여부는 미확인), `/orders/batch_cancel`, `/orders/close_position`, `/orders/preview` | 일부 미확인 |
| `client_order_id` | ID가 중복되면 주문을 새로 만들지 않고 기존 주문을 돌려준다고 문서에 적혀 있다. 그러나 `DUPLICATE_CLIENT_ORDER_ID` 오류 코드도 있다 | 실제 동작 미확인 |
| 휴장 | 금요일 17–18시(뉴욕)와 분기별 3시간 점검. 휴장 중에는 지정가·지정가 손절 주문만 대기시킬 수 있고 시장가는 불가하다. 기존 TP/SL은 재개장 가격으로 체결된다. 휴장 중에는 청산되지 않는다 | 확인됨 (손절 주문의 휴장 중 유지는 미확인) |
| WebSocket | `user` 채널(주문·포지션), `futures_balance_summary`, `heartbeats`, `ticker`. 채널마다 구독에 JWT가 필요하고 `sequence_num`으로 누락을 감지한다. 사용자 채널은 계정당 연결 1개다 | 확인됨 |
| 요청 한도 | WS는 IP당 초당 8회. REST 한도는 문서에 없고 응답 헤더 `x-ratelimit-*`로 알 수 있다 | REST 미확인 |
| 테스트 환경 | sandbox는 고정 응답만 주고 `/cfm/*` 엔드포인트를 지원하지 않는다. 실제 검증은 `preview`와 1계약 실주문으로 한다 | 확인됨 |
| 펀딩·청산 | 펀딩은 매시간 발생하고 평일 00:00(뉴욕)경 정산된다. 증거금 비율이 100%가 되면 청산되고 미체결 주문도 취소된다. 80%와 90%에 경고가 온다. 오후 4시(뉴욕)에 장중에서 오버나이트 증거금으로 바뀐다 | 확인됨 |
| 수수료 | 거래소 수수료는 BIP 계약당 편도 $0.10이다(자동매매는 Professional 등급으로 분류되지만 금액은 같다). 전체 비용은 "최저 0.02%, 계약당 최소 $0.15"다. 실제 등급은 `GET /transaction_summary`로 확인한다 | 확인됨, 계정 등급은 미확인 |
| SDK | `coinbase-advanced-py` 1.8.4(2026-06-19)로 고정한다. 선물 REST와 `WSUserClient`를 지원한다. 2.0.0rc1은 쓰지 않는다 | 확인됨 |
| 미확인 | 뉴욕 거주자의 CFM 선물 계좌 승인 여부(신청해야 알 수 있다), REST 요청 한도, API 서버 위치 | — |

## 3. 구조

### 3.1 원칙
- **전략 지문 대상 파일은 수정하지 않는다.** 대상은 `types.py`, `config.py`, `indicators.py`, `data/candles.py`, `waves/`, `strategy/`, `engine/`, `execution/`, `risk/`다. 새 패키지 `src/ewbot/live/`만 추가하므로 표본 외 거래 카운터가 유지된다.
- **판단은 목표 상태 재계산과 상태 맞추기로 한다.** 매 사이클마다 고정 엔진을 2017년부터 다시 계산해 목표 상태(지금 있어야 할 포지션, 손절, TP)를 구하고, 거래소의 실제 상태를 그 목표에 맞춘다. 모의매매(Plan 2)와 같은 방식이다.

### 3.2 구성 요소 (`src/ewbot/live/`)

| 모듈 | 역할 |
|---|---|
| `scheduler` | 매시 정각 30초 후에 판단 사이클을 실행한다 |
| `target` | 엔진을 재계산해 목표 상태를 만든다. 파라미터는 `holdout.lock`, 프로파일은 conservative다 |
| `exchange` | Coinbase API 래퍼다. 주문, 포지션, 잔고, 장 운영 상태, 미리보기를 다룬다 |
| `reconcile` | 목표와 실제의 차이를 행동 목록으로 만든다 |
| `watchdog` | 상시 감시를 맡는다. 손절 갭, 체결, 증거금, 장 운영 상태를 본다 |
| `journal` | SQLite에 주문 의도(전송 전에 먼저 기록), 체결, 포지션, 이벤트, 단계 이력을 남긴다 |
| `control` | 텔레그램 명령 `/status`, `/pause`, `/resume`, `/flatten`(확인 절차 포함)을 처리한다. 등록된 chat ID만 받는다 |
| `stage` | 운영 단계 SHADOW → CANARY → FULL을 관리한다 |
| `health` | 1분마다 외부 감시 서비스로 생존 신호를 보낸다. 신호가 3분 끊기면 경보를 보낸다 |

### 3.3 신호와 체결의 가격 기준
- 신호는 현물 BTC-USD 1시간봉으로 계산한다. 모의매매와 입력을 같게 하기 위해서다.
- 주문은 BIP 선물로 낸다. 손절과 TP 가격은 주문 시점의 `선물 중간가 / 현물 중간가` 비율로 환산하고, $5 호가 단위로 맞춘다. 롱 손절은 아래로, 숏 손절은 위로 반올림해 보수적으로 맞춘다.

### 3.4 인프라
- 미국 동부 VPS(월 $5~7)에 Ubuntu 24.04와 Docker Compose를 쓴다. 컨테이너는 `restart: unless-stopped`로 두고, 보안 자동 업데이트를 켠다.
- API 키는 `view + trade` 권한만 주고 VPS IP에 묶는다. 시작할 때 `GET /key_permissions`를 확인해 `can_transfer`가 true이면 실행을 거부한다.
- 비밀값은 VPS에서 권한 600 파일로 보관한다. 저장소, 이미지, 로그에는 넣지 않는다.

### 3.5 모의매매와의 관계
- GitHub Actions의 모의매매는 계속 돌리며 독립 감사 역할을 맡긴다.
- 실거래 journal의 결정과 모의매매 ledger의 결정을 대조해, 다르면 경고한다.
- 알림은 같은 텔레그램 채팅으로 보내되 `[LIVE]`와 `[PAPER]` 접두어로 구분한다.

## 4. 주문 실행

### 4.1 판단 사이클
1. 최신으로 마감된 1시간봉을 받는다. 마감 후 2분이 지나도 받지 못하면 이번 사이클의 판단을 보류하고, 기존 보호 주문은 유지한다.
2. 엔진을 재계산해 목표 상태를 구한다.
3. 거래소 상태를 조회한다(포지션, 미체결 주문, 잔고와 증거금, 장 운영 상태).
4. reconcile로 행동 목록을 만들고 실행한다.

### 4.2 상황별 주문

| 상황 | 주문 |
|---|---|
| 진입 | `market_market_ioc`로 낸다. `client_order_id`는 거래 키에서 결정적으로 만들고, 전송 전에 journal에 기록한다 |
| 보호 주문 | 체결 직후 `trigger_bracket_gtc` 두 개를 건다. ① TP1 수량 + 손절, ② 나머지 수량 + TP2 + 손절. 1계약이면 묶음 하나(TP1 + 손절)만 건다 |
| TP1 체결 후 | ②의 손절을 본전으로 옮긴다 |
| 추적 손절 | `orders/edit`로 손절가를 바꾼다. 지원되지 않으면 새 주문을 먼저 걸고 기존 주문을 취소한다. 감소 전용 동작 덕분에 잠깐 겹쳐도 과잉 청산은 일어나지 않는다 |
| 시간 손절, 근거 소멸, 손실 차단, END | 묶음 주문을 취소하고 `close_position`(시장가)으로 청산한다 |
| 반대 신호 전환 | 청산이 확인된 뒤에 반대 방향으로 진입한다 |
| 손절 갭 | Coinbase 문서에 따르면 묶음 주문의 손절은 발동되면 손절가에서 **5%** 떨어진 지정가 주문이 된다(롱 손절은 5% 아래, 숏 손절은 5% 위). 출처는 Create Order 레퍼런스이며 2026-10-03에 확인했다. 가격이 그 지정가를 지나쳤는데 10초 안에 체결되지 않으면, 감시 모듈이 즉시 `close_position`으로 정리하고 경고한다 |

### 4.3 수량

| 단계 | 수량 |
|---|---|
| SHADOW | 주문을 내지 않는다. 냈을 주문을 기록하고 `preview`로 검증한다 |
| CANARY | 항상 1계약이다. 1계약의 리스크가 계좌의 2%를 넘는 신호는 건너뛰고 기록만 한다 (2026-10-19 개정: 2% → 15%, 문서 끝의 개정 기록 참조) |
| FULL | `risk.sizing.size_contracts`를 실제 잔고와 conservative 프로파일로 호출만 한다(전략 파일은 바꾸지 않는다). 첫 30일은 3계약을 상한으로 둔다 (2026-11-05 개정: 프로파일은 `FULL_RISK`, 위험 10%·레버리지 5배이고 3계약 상한은 없앴다, 문서 끝의 개정 기록 참조) |

- 진입 여부와 손절·TP 가격은 모의매매와 같다. 계약 수만 다르다.

### 4.4 시뮬레이션과 실제의 차이
- 사이클마다 실제 포지션을 목표에 맞춘다. 남은 수량은 시장가로 정리하고, 차이는 journal과 일일 요약에 남긴다.
- 차이가 생기는 예: 시뮬레이션에서는 TP1이 체결됐는데 실제 지정가 주문은 체결되지 않은 경우, 부분 체결, 슬리피지.

### 4.5 실거래 계층의 독립 안전장치
- 동시 포지션은 1개이고, 단계별로 최대 계약 수 상한을 둔다.
- 증거금
  - 진입 전에 오버나이트 증거금 기준 비율을 미리 계산해 70%를 넘으면 진입을 거부한다 (2026-11-05 개정: FULL은 거부 대신 한도 안의 최대 계약 수로 줄여 진입한다).
  - 80%에서 경고하고, 90%에서 포지션을 줄인다.
  - 오후 3시 30분(뉴욕)에 오후 4시 증거금 인상을 대비한 점검을 한다.
- 실계좌 기준으로 일일 −3%, 누적 −15%에 닿으면 전량 청산하고 정지한다. (2026-10-19 개정: SHADOW·CANARY의 일 손실 한도는 −20%. 2026-11-05 개정: FULL은 일 −20%, 누적 −30%. 문서 끝의 개정 기록 참조)
- 금요일 휴장 전후의 진입 금지(엔진의 blackout 규칙과 같다). 휴장 중에 필요해진 청산은 재개장 직후 실행한다.
- 시작 시 점검: 전략 지문이 기준값 `e0435223…`과 같은지, 키 권한, 상품 사양(0.01, $5)을 확인한다. 하나라도 실패하면 실행을 거부한다.

## 5. 장애 복구와 운영

### 5.1 장애 대응

| 상황 | 대응 |
|---|---|
| 재시작·재부팅 | journal과 거래소를 대조한다. 미확정 주문은 `client_order_id`로 조회한 뒤에만 다시 보낸다. 포지션이 있는데 보호 주문이 없으면 즉시 다시 건다 |
| VPS 다운 | 거래소에 걸린 묶음 주문이 계속 보호한다. 생존 신호가 3분 끊기면 외부 감시 서비스가 텔레그램 경보를 보낸다 |
| WS 끊김·순번 누락 | 지수 백오프로 재연결하고 REST로 다시 맞춘다. 60초 넘게 끊기면 REST 10초 폴링으로 감시를 이어간다 |
| API 오류·요청 한도 | 헤더 기반으로 속도를 조절하고 3회 재시도한다. 진입이 실패하면 건너뛰고, 청산이 실패하면 계속 재시도하면서 경보를 보낸다 |

## 8. 알려진 위험과 한계
- **뉴욕 계좌 승인**: 공개 문서로는 확정되지 않는다. 승인이 거절되면 IBKR(CME 마이크로 BTC) 어댑터로 설계를 다시 한다.
- **시장가 손절 부재와 5% 지정가 오프셋**: 손절이 발동돼도 손절가보다 최대 5% 불리한 가격에 체결될 수 있다. 예를 들어 손절 거리가 3%인 거래에서 갭이 최대폭으로 나면, 실제 손실은 계획한 1R의 약 2.7배(계좌의 약 2.7%)까지 커질 수 있다. 일일 −3% 서킷브레이커는 그다음 거래부터 적용된다. 5% 지정가마저 지나치면, 감시 모듈이 정리하기 전까지 10초 넘게 노출될 수 있다. VPS가 죽어 있으면 묶음 주문의 지정가에만 의존한다. CANARY에서 실제 손절 체결가를 측정해 이 위험을 확인한다.
- **현물 신호와 선물 체결의 차이**: basis 변동 때문에 손절·TP의 실제 의미가 미세하게 달라질 수 있다.
- **증거금 제도**: 오버나이트 증거금(21~26%)이 레버리지를 사실상 약 4배 이하로 제한한다. 보수 프로파일(3배)은 이 범위 안에 있다.
- **API 변화**: CANARY 진행 중에 §2의 미확인 사항을 실측으로 확정한다. FULL 전에 §2를 다시 확인한다.
- **CANARY의 표본**: 신호가 한 달에 한 번꼴이라 첫 달 CANARY 거래는 0~1건일 수 있다. CANARY 통과(완결 거래 3건)에는 수개월이 걸릴 수 있다.

## 개정 기록: 2026-10-19 CANARY 위험 한도 (사용자 결정)

사용자가 2026-10-19에 아래 세 가지를 결정했다. 4.3의 2% 규칙과 4.5의 일일 −3% 규칙은 당시 기록으로 남기고, 이 절이 SHADOW·CANARY에서 우선한다.

**바뀐 것**

- CANARY(와 SHADOW의 미리보기) 1계약 위험 한도: 계좌의 2% → **15%** (`CANARY_MAX_RISK`).
- 실계좌 일 손실 한도: SHADOW·CANARY에서 3% → **20%** (`LIVE_DAILY_LOSS`). FULL은 전략의 3%를 그대로 쓴다. 단계가 바뀌면 재시작 때 단계에 맞는 값이 적용된다.
- 실계좌 누적 손실 한도: **−15% 유지**.
- 모의 엔진의 서킷브레이커(`cfg.breakers`, 모의 자산 기준 −3%)와 목표 재생(`target.py`)은 그대로다. 달라지는 것은 실계좌 `AccountGuard`의 기준뿐이다.

**이유**

- 계좌가 약 $500이면 2% 한도(약 $10)에서는 홀드아웃 신호 36건 중 2건만 통과한다. CANARY가 사실상 시작되지 못한다. 15%(약 $75)면 28건이 통과한다.
- 일 한도 3%(약 $15)에서는 정상적인 손절 한 번이 손실 한도에 걸려 정지하고 CANARY 실패로 기록된다.

**감수하는 결과**

- 손절 한 번의 최대 손실이 약 $75(계좌의 15%)까지 커질 수 있다.
- 일 한도 20%가 누적 한도 15%보다 느슨하므로, 같은 최고점에서는 누적 −15%가 먼저 걸린다. 손실 한 건이 누적 −15%에 닿으면 전량 청산, 정지, CANARY 실패가 되고, 사용자가 이를 받아들였다.
- 전략 A 파일과 지문(`e0435223a3f9f1ef69c79b54541958f9634989b86728da02332f21d298bac5f1`)은 바뀌지 않는다. 50건 카운트도 그대로 유지된다.
- 실거래 계층의 코드가 바뀌므로 SHADOW 14일을 다시 시작한다.

## 개정 기록: 2026-11-05 FULL 위험 설정 (사용자 결정)

사용자가 2026-11-05에 FULL 단계에 한해 아래 네 가지를 결정했다. 4.3의 FULL 행(conservative 프로파일)과 4.5의 −3%/−15% 규칙, 2026-10-19 개정 기록의 "FULL은 전략의 3%를 그대로 쓴다"는 당시 기록으로 남기고, 이 절이 FULL에서 우선한다.

**바뀐 것 (FULL만)**

- 거래당 위험: 1% → **10%** (`FULL_RISK = RiskProfile("full", 0.10, 5.0)`, `live/pricing.py`).
- 실계좌 누적 손실 한도(최고점 대비): 15% → **30%** (`FULL_TOTAL_DD`, `live/watchdog.py`).
- 실계좌 일 손실 한도: 3% → **20%** (`LIVE_DAILY_LOSS`, 이제 모든 단계 공통).
- 레버리지 상한: 3배 → 거래소 한도까지(`FULL_RISK`의 5배). 거래소의 오버나이트 증거금은 롱 약 4.8배, 숏 약 3.9배다. 기존 오버나이트 증거금 70% 진입 점검(`MARGIN_ENTRY_MAX`)은 그대로 두며, 일부러 이 점검이 먼저 걸리게 했다. 70%는 명목 기준 롱 약 3.3배, 숏 약 2.7배이고, 이를 넘는 진입은 거부한다(이 항목은 아래 "추가 결정"으로 바뀌었다).

**바뀌지 않는 것**

- SHADOW·CANARY: 1계약, `CANARY_MAX_RISK` 15%, 일 −20%, 누적 −15%.

- 모의매매 재생과 `target.py`는 conservative 프로파일 그대로이므로 판단은 달라지지 않는다. 달라지는 것은 실거래 계층의 계약 수와 실계좌 `AccountGuard`의 기준뿐이다.
- 전략 A의 신호, 지문(`e0435223a3f9f1ef69c79b54541958f9634989b86728da02332f21d298bac5f1`), 홀드아웃 36건은 바뀌지 않는다.

**감수하는 결과**

- 실거래 계층의 코드가 바뀌므로 배포하면 SHADOW 14일을 다시 시작한다.
- 지금까지의 백테스트와 모의매매 수치는 위험 1% 기준이다. 위험 10%에서의 낙폭은 이 수치로 설명되지 않는다. 같은 거래열이라도 손실 한 건이 계좌의 10% 안팎이고, 연속 손실이 이어지면 −30% 누적 한도에 닿을 수 있다.
- 손절이 5% 지정가 오프셋을 넘어 체결되면 한 건의 손실이 계획한 1R(계좌의 10%)을 넘을 수 있다. 오프셋 안에서(손절가보다 5% 불리한 지정가에) 체결되어도 1R을 넘는다. 10% 위험이 정하는 가장 좁은 손절(70% 증거금 한도가 먼저 걸리지 않는 경계, 롱 기준 진입가의 약 2.9%)에서는 계약 수가 계좌의 약 3.3배 명목이고, 손실이 약 3.3 × (2.9% + 5%) ≈ 계좌의 **26%** 까지 커진다(숏은 약 23%). 10초 갭 감시는 이 오프셋을 넘어선 갭을 막지 못한다. 가격이 지정가를 지나쳐도 감시가 시장가로 닫기까지 10초 넘게 포지션이 열려 있고, 그동안의 손실에는 상한이 없다. 청산은 증거금 비율이 100%가 될 때 일어난다(3.1절). 오버나이트 숏 증거금률 25.66%에서 70% 한도까지 쓰면 레버리지는 약 2.73배이고, 잔고 1 − 2.73m = 0.70 × (1 + m)에서 **가격이 약 8.75% 오르면 청산**된다. 70% 한도가 걸리는 가장 넓은 숏 손절(약 3.56%)의 지정가는 약 8.74%라 거의 같으므로, 이 경우 지정가를 넘는 갭은 청산으로 이어질 수 있다. 롱은 3.33배에서 약 11.4%이고 지정가는 약 7.8%다. `risk.sizing`의 청산 검사는 유지 증거금을 0으로 보므로 이 위험을 잡지 못한다. 위 수치는 증거금 비율 100% 기준의 계산이며, 실제 청산 규칙은 CANARY·FULL 첫 거래 전에 거래소 자료로 확인한다.
- 증거금률은 바뀔 수 있다. 런타임은 시작 때 읽은 값에 의존하지 않고 진입을 정하기 직전마다, 그리고 15분마다(증거금 감시용) 거래소에서 다시 읽는다. 증거금률이 오르면 같은 위험으로도 진입 계약이 줄고, 이미 열린 포지션의 증거금 비율이 70%를 넘어 80% 경고·90% 축소에 닿을 수 있다. 새로 읽지 못하거나 쓸 수 없는 값(없음, 0, 유한하지 않음)이면 그 진입은 거부하고 감시는 마지막 정상 값을 쓴다.
- FULL에서 CANARY로 강등되면(자동 강등과 수동 강등 모두) 실계좌 최고점은 강등 뒤 첫 잔고 조회 값으로 다시 잡힌다. FULL의 최고점을 CANARY의 15% 한도로 재면 −15%~−30% 손실에서 강등 직후 TOTAL_DD가 발동하기 때문이다. 손실 한도 발동의 전량 청산, 정지, 중대 사건은 그대로다.
- FULL에서 손실 한도가 발동하면 전량 청산, 정지, 중대 사건(CANARY로 강등)이 되며 이 규칙은 바뀌지 않았다.

**추가 결정 (2026-11-05, 같은 날): FULL의 증거금 진입 한도는 거부가 아니라 축소**

- FULL에서 위험 10% 기준 계약 수가 오버나이트 증거금 `MARGIN_ENTRY_MAX`(70%)를 넘으면 진입을 거부하지 않고, 한도 안에 드는 최대 계약 수(`pricing.max_contracts_for_margin`)로 진입한다. 진입 계약 수는 위험 기준 계약 수, FULL의 3계약 상한(`stage.full_cap`), 증거금 최대치 중 가장 작은 값이다. 한 계약도 들어가지 않으면(최대치 0) 예전과 같은 메시지로 거부한다.
- 그래서 **실제 위험은 10%보다 작을 수 있다.** 진입한 계약의 실제 위험은 `risk_per_contract(진입가, 손절가, 비용) × 진입 계약 / 자산`이다. 5배 상한이나 신호의 `risk_mult`(예: 0.5)가 필요 계약을 이미 줄였을 수 있으므로 "10% × 진입 / 필요"로 근사하지 않는다(그 식은 틀린다). 줄어든 진입은 저널(`ENTRY_REDUCED`)과 알림(`[진입 축소]`)에 필요 계약과 진입 계약으로 남는다.
- SHADOW·CANARY는 1계약이므로 70%를 넘으면 예전처럼 거부한다. 증거금 경고·축소 기준(80%·90%)은 바뀌지 않는다. 한도 바로 아래(70%)에 진입한 포지션은 감시가 곧바로 건드리지 않는다.
- FULL에서 손실 한도(일 −20%, 누적 −30%)가 발동하면 전량 청산, 정지, 중대 사건으로 **CANARY로 강등**된다. 이 규칙은 그대로이며, 두 번째 결정은 "변경 없음"이다.

## 개정 기록: 2026-11-05 FULL 시작 기준에서 표본 외 50건 제외 (사용자 결정)

사용자가 2026-11-05에 FULL 시작 기준에서 모의매매 3번(표본 외 50건)을 뺐다. 위 6.1절 FULL 행과 일정 결정의 "표본 외 50건" 기준은 처음 설계의 기록으로 남기고, 이 절이 우선한다.

**이유**

- 거래가 한 달에 한 건꼴이면 50건을 채우는 데 약 13개월이 걸린다. 그때까지 FULL을 열 수 없다.

**바뀐 것**

- FULL은 실거래 거래가 적어도 시작할 수 있다. 시작 전제는 CANARY 통과 기준, 모의매매 1·2·4번, 거래 권한 키(송금 권한 없음), 사용자 승인이다. 3번(표본 외 50건)만 빠졌고 나머지 관문은 그대로다.
- 구현: `live/stage.py`의 `_paper_gates`는 SHADOW→CANARY와 CANARY→FULL에 같은 모의매매 관문(1·2·4번)을 쓴다. `G_C3` 관문은 없어졌다.
- 예상 시점: 첫 신호가 나와야 하고 CANARY 통과(완결 거래 3건 또는 90일, 보호된 진입 1건 이상)를 거쳐야 하므로 빨라야 약 4개월이다.

**바뀌지 않는 것**

- FULL의 첫 30일 3계약 상한(`FULL_CAP_CONTRACTS`, `FULL_CAP_DAYS`).
- 모의매매 런타임 자체의 4기준 판정과 `36/50` 표시, 홀드아웃(`GO_LIVE_MIN_TRADES`), 전략 A 파일과 지문, 50건 카운트. `ewbot paper status`와 모의매매 알림은 계속 50건 기준의 3번 판정을 보여 주지만, 실거래 FULL 승급에는 쓰이지 않는다.

**감수하는 결과**

- FULL의 위험 10%는 표본 외 50건의 통계적 확인 없이 시작한다. 지금까지의 수치(홀드아웃 36건)는 위험 1% 기준이며, 이 결정은 그 확인 없이 더 큰 규모를 여는 것이다.

## 개정 기록: 2026-11-05 며칠 안에 FULL까지 (사용자 결정)

사용자가 2026-11-05에 신호를 기다리지 않고 며칠 안에 FULL까지 가기로 결정했다. 이 결정의 번복을 권하지 않는다. 6.1·6.2와 이전 개정 기록의 "코드가 바뀌면 SHADOW 14일을 다시 시작한다", "FULL의 첫 30일 3계약 상한은 바뀌지 않는다", "빨라야 약 4개월"은 당시 기록으로 남기고, 이 절이 우선한다.

**바뀐 것**

1. **SHADOW → CANARY에 신호가 필요 없다.** "신호 1건 이상"은 필수에서 빠졌다. ①은 비교한 판단이 0건이면, ③은 preview가 0/0이면 통과한다. 비교나 preview가 있는데 불일치·거부가 있으면 그대로 실패하고, 감사가 실패했거나 오래됐거나 돌지 않았어도 실패한다. ②와 ④, 모의매매 1·2·4번, 거래 키, 평탄한 장부, `--confirm`은 그대로다.
2. **코드 배포가 SHADOW를 다시 시작하지 않고, 14일 최소도 면제한다.** 확인 결과 이 재시작은 코드가 아니라 운영 규칙이었다(README, 런북, 이 명세). `restart_stint`는 사용자가 `ewbot live stage ... --restart`로 실행할 때만 돌고, `deploy.sh`와 런타임은 코드 버전이나 지문으로 단계를 다시 시작한 적이 없다. 그래서 문서를 고치고 `SHADOW_MIN_DAYS`를 없앴다. 배포는 같은 단계 구간의 재시작 한 번이고 ④의 복구 기록이 하나 늘 뿐이다. 면제된 두 항목은 `ewbot live status`에 `[면제]`로 계속 보인다.
3. **CANARY → FULL의 "완결 거래 3건 또는 90일"과 보호 관문을 시험 거래 1건 성공으로 충족한다.** 시험 거래의 실측 수수료로 ⑤ 비용 관문도 충족한다. 시험 거래는 전략 거래로 세지 않으므로 그렇지 않으면 ⑤는 신호 없이 영영 충족되지 않기 때문이다(이 부분은 구현 중 내린 판단이다). ②③④, 중대 사건 없음, 일시 정지 아님, 최근 감사(비교 0건은 통과), 모의매매 1·2·4번, 거래 키, `--confirm`은 그대로다. 단계 구간을 다시 시작하면 시험 거래도 다시 해야 한다.
4. **`ewbot live test-trade --confirm [--side long|short]`를 추가했다.** CANARY에서만 1계약을 시장가로 진입하고, 전략 거래와 같은 경로로 보호 주문을 걸고(손절·익절은 중간가에서 2%), 거래소에서 손절을 확인한 뒤 같은 경로로 청산하고, 평탄함을 확인해 `TEST_TRADE` 이벤트로 기록한다. 포지션이 열린 동안 `GET /api/v3/brokerage/cfm/balance_summary`의 증거금 필드를 원본 그대로 기록하고 출력한다(`TEST_TRADE_MARGIN`). Coinbase가 BIP의 유지 증거금률을 공개하지 않아 이것이 실측 수단이다. 이 조회는 경고만 하고 청산을 막거나 늦추지 않는다(별도 스레드, 최대 2초 대기).
   - 프로세스 사이의 잠금은 없고, 다른 프로세스의 포지션이나 브래킷은 런타임의 다음 확인에서 청산·취소되며 수동 개입(`UNKNOWN_POSITION` 등)으로 읽힌다. 그래서 명령은 저널로 요청만 하고(`ewbot live rebase`와 같은 방식), 돌고 있는 런타임이 자기 루프의 한 틱 안에서 실행한다. 매시 55분~06분에는 거부한다.
   - 거래 번호를 첫 주문 전에 기록하므로 완결 거래 수와 비용 보고에 들어가지 않는다. 엔진 판단이 없으므로 모의매매 대조에도 나타나지 않는다. 잔고에는 스프레드와 수수료만큼 반영되며 손실 한도는 이를 보통 손실로 읽는다.
   - 진입 뒤 단계가 실패하면 청산 요청을 저널에 세우고(`TEST_TRADE_FAILED`) 진입을 일시 정지한다. 포지션은 청산되거나, 손절 주문으로 보호된 채 매 확인마다 청산을 다시 보낸다. 프로세스가 도중에 죽으면 다음 시작이 같은 일을 한다.
5. **FULL의 3계약 30일 상한을 없앴다.** `full_cap`은 FULL에서 첫 분부터 `None`이고(CANARY 1, SHADOW 0), 크기는 min(위험 10%, 5배, 70% 오버나이트 증거금 안의 최대)이다. `FULL_CAP_DAYS`와 깨끗한 기간 계산을 지웠다. 수동 개입이 아직 남아 있는 동안(거래소에 남은 외부 주문) 3계약으로 묶는 규칙은 30일과 무관하므로 유지했다. FULL에서 중대 사건이 아닌 CANARY 실패는 기록하고 알리기만 한다.

**바뀌지 않는 것**

- 손실 한도(FULL 일 −20%, 누적 −30%, CANARY로 강등), 감시 장치, 증거금률 재조회, 승급의 `--confirm`과 평탄한 장부, 키 권한(거래 가능, 송금 불가).
- 전략 A 파일과 지문(`e0435223a3f9f1ef69c79b54541958f9634989b86728da02332f21d298bac5f1`), `holdout.lock`, 백테스트, 모의매매, 홀드아웃 36건.

**잃는 것**

- **신호 기반 SHADOW 대조가 없다.** 비교할 판단이 0건이면 ①과 ③은 아무것도 확인하지 않고 통과한다. 실제 신호에서 실거래 판단이 모의매매와 같은지, 그 신호의 주문이 `preview`를 통과하는지 보지 않은 채 실주문으로 넘어간다.
- **새 코드를 실제 운영에서 관찰하지 않는다.** 2026-10-19 이후의 실거래 계층 변경(FULL 위험 설정, 증거금 재조회, 강등, 이번 시험 거래)은 테스트만 거쳤고 14일 관찰 없이 배포된다.
- **FULL은 신호로 움직인 실거래 없이 시작한다.** 시험 거래는 1계약 왕복 하나다. 손절·익절 체결, 5% 지정가, 갭, 손절 이동, TP1 본전, 두 묶음 브래킷, 수량 축소, 부분 체결, 금요일 휴장, 실제 슬리피지는 시험 거래로 확인되지 않는다. 런북 `Confirm during CANARY`와 `Before FULL`의 대부분은 FULL에서 처음 답이 나온다.
- **3계약 단계적 확대가 없다.** 첫 실제 신호부터 위험 10%, 상한 없는 크기로 들어간다. 위의 미확인 경로가 처음 돌아가는 거래가 곧 전체 크기다.
- 증거금 실측은 1계약, 한 시점의 값이다. 크기에 비례하는지는 보여 주지 못한다. FULL 위험 설정 개정의 청산 계산(숏 약 8.75%, 유지 증거금 0 가정)은 이 값으로 다시 확인한다.
- 거래 빈도는 그대로 한 달 한 건 정도이므로, FULL에 며칠 안에 도달해도 첫 전략 거래가 며칠 안에 나온다는 뜻은 아니다.
