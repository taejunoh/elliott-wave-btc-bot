# ewbot Plan 2 — 모의매매(paper) 런타임 설계 명세

- 작성일: 2026-10-02
- 상태: 사용자 승인됨 (구현 계획 작성 전)
- 상위 명세: `docs/superpowers/specs/2026-10-01-elliott-wave-btc-bot-design.md` (이하 "Plan 1 명세")

## 1. 배경과 목표

### 배경
- Plan 1 홀드아웃이 2026-10-02에 1회 실행되었다(`holdout.lock`, 커밋 `64e628a`).
  - 파라미터: K4 = 2.0, Q_MIN = 0.7, S_MIN = 0.5
  - 홀드아웃 구간: 2024-01-01 ~ 마지막 봉 2026-10-02 11:00 UTC(`last_bar_ts = 1790938800`)
  - A 전략 결과: 표본 외 거래 36건, 샤프 0.97, 최대 낙폭 2.9%
- Plan 1 명세 §9.6 실거래 전환 기준 중 1·2번은 충족했다. 3번(표본 외 거래 50건 이상)과 4번(paper 모드 최소 4주 운영)은 미충족이다.

### 목표
- 고정된 전략과 파라미터로 표본 외 거래를 계속 쌓는다. 목표는 합계 50건이고, 남은 것은 최소 14건이다.
- 4주 이상 운영하면서 "실시간으로 기록한 결정 = 나중에 다시 계산한 결정"을 검증한다.
- 사람이 따로 서버를 관리하지 않아도 매시간 자동으로 돌아가고, 결과를 텔레그램과 리포트로 받아 본다.

### 비목표
- 실제 주문, Coinbase API 키, 실시간 웹소켓
- VPS
- 텔레그램 명령(`/pause` 등), 대시보드 서버

이것들은 실거래 단계 설계에서 다룬다.

## 2. 핵심 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 실행 장소 | GitHub Actions 예약 실행. 실거래 단계에서 VPS로 이전 | 서버 관리 없음, 비용 없음, 기록이 git에 남음. 재계산 방식이라 실행이 늦거나 빠져도 결과가 같음 |
| 구현 방식 | **매 실행마다 2017년부터 전체를 결정적으로 재계산(방식 A)** | 백테스트와 구조적으로 같은 결과가 나오고, 엔진 상태를 따로 저장할 필요가 없음. 전략 코드를 바꾸지 않으므로 전략 지문이 유지됨 |

| 변경 정책 | **엄격**: 전략 지문이 바뀌면 새 구간을 시작하고 카운터를 0으로 리셋 | 표본 외 검증의 의미를 지키기 위함 |
| 알림·리포트 | 텔레그램 푸시 알림. 기록과 리포트는 저장소의 `paper` 브랜치에 커밋 | Actions는 계속 떠 있는 프로세스가 아니어서 명령 수신이나 서버를 둘 수 없음 |

## 3. 구조

기존 모듈은 수정하지 않는다. 새 패키지와 CLI 하위 명령, 워크플로만 추가한다.

```
src/ewbot/paper/
  fingerprint.py  전략 지문 계산과 기준값 비교
  ledger.py       모의매매 기록(JSON) 모델과 원자적 읽기·쓰기
  runner.py       1회 실행 오케스트레이션
  notify.py       텔레그램 전송과 메시지 포맷
  report.py       모의매매 HTML 리포트 (backtest/report.py 재사용)
src/ewbot/cli.py  `paper run`, `paper status` 하위 명령 추가 (전략 지문 대상 아님)
.github/workflows/paper.yml
paper 브랜치(코드 이력과 분리):
  ledger.json  report.html  runs.log
```

- Plan 1 명세 §3의 실행 모드 `paper`(실시간 시세 + PaperBroker)는 이 문서에서 "시간봉 단위 결정적 재계산"으로 구체화한다.
- 웹소켓 기반 실시간 실행기는 실거래 단계에서 이 재계산 결과를 매 봉 검증 기준으로 삼는다.

## 4. 실행 흐름 (`ewbot paper run`, 매시 1회)

1. **입력 고정**
   - 파라미터는 `holdout.lock`의 `params`만 쓴다.
   - 리스크는 conservative 프로파일이고, 서킷브레이커는 켜져 있다.
   - 비용 모델은 Plan 1 기본값과 같다.
   - CLI에는 파라미터나 설정을 바꾸는 옵션이 없다.
2. **사전 검증** (하나라도 실패하면 아무것도 커밋하지 않고 종료하며 실패를 알린다)
   - `holdout.lock`이 존재하고 git에 커밋되어 있으며 작업 트리에서 변경되지 않았다.
   - 잠금 파일의 `params`가 grid 조합이다.
   - 잠금 파일의 `sha256`이 현재 `BotConfig` 기본값으로 다시 계산한 `lock_digest(BotConfig(), params, random_runs, code_sha256)`와 같다. 기본값(`config.py`)이 바뀌면 새 구간을 여는 대신 매 실행이 사전 검증에서 멈추고 실패를 알린다. 되돌리면 다시 실행된다. 새 구간이 열리지 않았으므로 구간 1과 홀드아웃 36건은 그대로 합산된다(멈춘 시간은 4번 기준의 커버리지에서 빠진다).
3. **데이터 갱신**
   - Actions 캐시에서 `data/cache/BTC-USD_1h.parquet`을 복원한다. 캐시가 없으면 전체를 받는다.
   - `update_cache`로 마감된 봉을 뒤에 덧붙인다. 재시도는 3회까지다.
   - 이번 실행에 쓴 데이터의 해시를 계산한다.
4. **전략 지문 확인**: 현재 지문을 기준값과 비교한다(§5.1). 다르면 새 구간을 시작한다(§5.2).
5. **전체 재계산**
   - `TradingEngine`을 2017-01-01부터 마지막 마감 봉까지 실행한다.
   - 이 경로는 `allow_holdout=True`를 쓰는 유일한 비(非)홀드아웃 호출자다.
6. **표본 외 추출**: 진입 시각 `entry_ts > holdout_last_bar_ts`인 종료된 거래와, 현재 열려 있는 포지션을 뽑는다.
7. **직전 기록과 비교**
   - 새 진입, 손절 이동(본전·추적), 새 청산을 이벤트로 만든다.
   - 이미 기록된 과거 결정이 그대로 재현되는지 검증한다(§5.3).
8. **기록**: `ledger.json`, `report.html`, `runs.log`를 원자적으로 갱신한다. 임시 파일을 쓴 뒤 교체하는 방식이다.
9. **알림**: 아직 보내지 않은 이벤트만 텔레그램으로 보낸다(§6.3). 보낸 이벤트 ID는 기록에 남긴다.
10. **커밋**: 워크플로가 `paper` 브랜치에 커밋하고 푸시한다. 충돌이 나면 최신 상태를 받아 4~9단계를 다시 수행한다.

### 모의매매 성과
- 자산 곡선과 지표는 재계산 결과 중 `ts > holdout_last_bar_ts` 구간만 잘라 계산한다. `compute_metrics`의 window를 쓴다.
- 실거래 전환 판정용 "표본 외 합계"는 기준 지문 구간의 거래만 센다. 구성은 홀드아웃 거래(잠금 파일의 `n_trades.A` = 36)에 모의매매 거래를 더한 것이다.

## 5. 연구 정직성 장치

### 5.1 전략 지문
- **포함 파일**: `src/ewbot/types.py`, `config.py`, `indicators.py`, `data/candles.py`, `waves/**/*.py`, `strategy/**/*.py`, `engine/**/*.py`, `execution/**/*.py`, `risk/**/*.py`
- **제외 파일**: `data/coinbase_history.py`, `backtest/**`, `cli.py`, `paper/**`
- **계산식**: `sha256( for path in sorted(paths): path + "\0" + bytes + "\0" )`
  - 주석이나 공백 변경도 지문을 바꾼다. 엄격 정책이다.
- **기준값**: 홀드아웃 커밋 `64e628a`의 같은 파일 집합으로 계산한다. 기록 초기화 때 `git show 64e628a:<path>`로 한 번 계산해 `ledger.json`에 저장한다. 커밋 해시도 함께 저장한다.

### 5.2 구간(epoch)
- `ledger.epochs[]`의 각 원소는 `{id, fingerprint, started_ts, reason}`이다.
- 실행 시점의 지문이 마지막 구간의 지문과 다르면 새 구간을 추가하고 텔레그램 경고를 보낸다.
- 거래마다 `epoch_id`를 기록한다.
- 실거래 전환 판정에는 **지문이 기준값과 같은 구간의 거래만** 쓴다. 다른 구간의 거래는 리포트에 따로 표시만 한다.

### 5.3 실시간 결정 재현 검사 (Plan 1 명세 §9.6의 4번)
- 실행마다 그 시점에 확정된 결정을 `decisions[]`에 남긴다.
  - 대상: 진입 신호, 체결(진입·TP·손절·청산), 손절 이동
  - 형식: `(kind, ts, price, contracts, reason)`
  - 기록 시점의 `run_id`와 데이터 해시를 함께 남긴다.
- 이후 실행은 이미 기록된 결정이 이번 재계산에서도 같은지 확인한다. 가격은 1e-9 상대 오차까지 허용한다.
- 다르면 불일치로 기록하고 원인을 다음과 같이 분류한다.
  - `DATA_REVISION`: 해당 시점 이전 봉의 해시가 변함
  - `FINGERPRINT_CHANGE`: 구간이 바뀜
  - `ENVIRONMENT_CHANGE`: 결정을 기록한 실행과 현재 실행의 실행 환경이 다름. 단, 실행 환경 다이제스트가 직전 성공 실행과 달라진 뒤의 첫 실행에서만 적용한다. 매 실행이 기록된 결정을 모두 다시 검사하므로, 새 환경의 실행이 한 번 재현한 결정이 이후 달라지면 `UNEXPLAINED`다. 실행 환경은 Python 버전, OS와 머신 아키텍처(`platform.system()`·`platform.machine()`), numpy·pandas·pyarrow 버전, `uv.lock` 해시, 실행기 이미지의 `ImageOS`다. `ImageVersion`은 매 실행에 기록하지만 비교하지 않는다(GitHub가 이미지를 매주 갱신해서, 비교하면 이후 모든 `UNEXPLAINED`가 `ENVIRONMENT_CHANGE`로 가려진다). Python은 패치 버전까지 `3.12.13`으로 고정한다. 이 경우 경고하고 리포트에 표시하지만 4번 기준의 `UNEXPLAINED` 집계에는 넣지 않는다(2026-10-02 사용자 결정).
  - `UNEXPLAINED`: 그 밖의 경우
  - 분류 우선순위: `DATA_REVISION` → `FINGERPRINT_CHANGE` → `ENVIRONMENT_CHANGE` → `UNEXPLAINED`
- 4번 기준은 다음을 모두 만족하면 충족이다.
  - 모의매매 연속 운영 28일 이상
  - 그 기간의 `UNEXPLAINED` 불일치 0건
  - 매시간 실행 커버리지 95% 이상. 커버리지는 성공한 실행 시각을 시간 단위로 센 것이다.

### 5.4 데이터 무결성
- 캐시는 append-only다. 실행마다 사용 데이터 해시를 `runs[]`에 기록한다.
- 홀드아웃 구간 데이터 해시를 `holdout.lock`의 데이터 지문과 대조한다.
  - 불일치하면 경고와 기록만 하고 실행은 계속한다.
  - 표본 외 거래는 홀드아웃 이후 구간이라 카운트에는 영향이 없다. 다만 재현성이 손상되었다는 기록으로 남긴다.

### 5.5 실거래 전환 판정 표시
리포트 맨 위에 Plan 1 명세 §9.6의 1~4번 상태를 표시한다.
- **1·2번**: 표본 외 전체 구간(2024-01-01 ~ 현재, 기준 지문 구간)에서 A·HYBRID와 C·BH·EMA·RANDOM을 같은 기간으로 다시 비교한다. 이 비교는 하루 1회, 일일 요약 실행 때만 계산한다(RANDOM 100회 비용 때문).
- **3번**: `표본 외 거래 N/50`
- **4번**: §5.3의 충족 여부
- 네 가지를 모두 충족하면 "실거래 전환 검토 가능"이라고 표시한다. **자동 전환은 하지 않는다.**

## 6. 운영

### 6.1 워크플로 `paper.yml`
- **트리거**: 주 트리거는 외부(Cloudflare Workers cron)가 매시 37분(UTC)에 호출하는 `workflow_dispatch`다. `schedule: cron "52 */3 * * *"`(3시간마다 52분)는 드물게 도는 백업이다. 입력 없는 `workflow_dispatch`는 수동 실행도 겸한다. (2026-10-03 변경: GitHub `schedule`이 부하 때 실행을 누락한다. 매시 `7 * * * *` 약 13회 중 2회만 실행되어 4번 기준의 커버리지를 지킬 수 없었다. 커버리지는 트리거와 무관하게 성공 실행이 있는 시간을 센다. 설정은 `docs/paper-trading.md`의 "Reliable hourly trigger".)
- **동시성**: `concurrency: {group: paper, cancel-in-progress: false}`
- **권한**: `contents: write`
- **단계**
  1. `master`를 체크아웃한다.
  2. `paper` 브랜치를 별도 작업 디렉터리에 체크아웃한다. 브랜치가 없으면 orphan으로 생성한다.
  3. uv를 설치한다. uv 캐시와 `data/cache`는 Actions 캐시로 복원한다.
  4. `uv sync --frozen`
  5. `uv run ewbot paper run --ledger-dir <paper worktree>`
  6. 변경이 있으면 커밋하고 푸시한다.
  7. 실패하면 `if: failure()` 단계에서 텔레그램 실패 알림을 보낸다(토큰이 있을 때).
- **예상 사용량**: 1회 약 1분, 월 약 720분. 비공개 저장소 무료 한도 2,000분 이내다.

### 6.2 `paper` 브랜치
- 코드 이력과 분리된 기록 전용 브랜치다.
- `ledger.json`
  - 스키마 버전
  - 기준 지문, 기준 커밋
  - holdout 요약(`last_bar_ts`, params, n_trades)
  - `epochs[]`, `trades[]`, `open_position`, `decisions[]`, `discrepancies[]`, `runs[]`, `sent_event_ids[]`
- `report.html`
  - 실거래 전환 판정
  - 표본 외 자산 곡선과 낙폭
  - 거래 표와 거래별 스냅샷 차트
  - 현재 1등 카운트
  - 불일치 목록
- `runs.log`: 한 줄에 한 실행씩 기록한다(시각, 상태, 데이터 해시, 거래 수).

### 6.3 텔레그램
- **비밀값**: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`(GitHub Secrets). 값이 없으면 전송만 건너뛰고 실행은 성공으로 처리한다.
- **이벤트**

| 이벤트 | 내용 |
|---|---|
| 신규 진입 | 셋업, 방향, 진입가, 손절, TP1·TP2, blended R, 1등 카운트(q, S_rev) |
| 손절 이동 | 본전 이동 또는 추적 손절 갱신 |
| 청산 | 사유, 손익, R, 표본 외 누적(N/50) |
| 일일 요약 | 뉴욕 시간 09:00 이후 첫 실행. 포지션, 자산, 누적 거래, 전환 판정 |
| 경고 | 구간 리셋, 불일치, 데이터 해시 불일치, 실행 공백(직전 성공 실행에서 3시간 초과) |
| 실패 | 실패 단계와 실행 로그 링크 |

- **중복 방지**: 이벤트 ID는 `kind:ts:trade_key`이고, `sent_event_ids`에 있으면 다시 보내지 않는다.
- **전송 실패**: 3회 재시도한 뒤 기록하고 실행은 계속한다. 보내지 못한 이벤트는 다음 실행에서 다시 시도한다.

### 6.4 장애 처리

| 상황 | 대응 |
|---|---|
| 시세 수집 실패 | 3회 재시도 후 종료한다(커밋 없음). 실패를 알리고, 다음 실행이 빠진 봉까지 재계산한다 |
| 캐시 유실 | 전체 다시 받기(약 70초). 과거 봉이 바뀌었으면 §5.3에서 `DATA_REVISION`으로 분류한다 |
| 푸시 충돌 | 최신 `paper` 브랜치를 받아 재계산한 뒤 다시 푸시한다(최대 3회) |
| Actions 중단 | 실행 안에서는 감지할 수 없다. GitHub 실패 이메일과 "일일 요약 미수신"이 경보 역할을 한다 |

### 6.5 사용자가 직접 할 일
1. 텔레그램 @BotFather로 봇을 만들고 토큰을 받는다.
2. 봇에게 메시지를 1회 보낸다. chat ID 확인 방법은 Claude가 안내한다.
3. `gh secret set TELEGRAM_BOT_TOKEN`, `gh secret set TELEGRAM_CHAT_ID`를 실행한다. 값은 사용자가 직접 입력한다.

## 7. 테스트

### 7.1 단위 테스트

| 대상 | 내용 |
|---|---|
| 전략 지문 | 파일 집합이 정확한지, 파일 순서와 무관한지, 주석 1줄 변경으로 값이 바뀌는지, `64e628a` 기준값을 git에서 재계산할 수 있는지 |
| 기록 파일 | 스키마 왕복, 원자적 쓰기(중간 실패 시 원본 보존), 스키마 버전 검사 |
| 구간 | 지문이 바뀌면 새 구간이 생기고 기준 구간 카운트가 0이 되는지, 이전 구간 거래가 보존되는지 |
| 표본 외 추출 | 홀드아웃 종료 시점에 열려 있던 포지션 제외, `entry_ts == last_bar_ts` 경계 |
| 직전 기록과 비교 | 진입·손절 이동·청산 이벤트 생성, 같은 이벤트 중복 방지 |
| 재현 검사 | 과거 봉 1개 변경 시 `DATA_REVISION`, 구간 전환 시 `FINGERPRINT_CHANGE`, 실행 환경이 바뀐 뒤 첫 실행에서 `ENVIRONMENT_CHANGE`(이미 새 환경에서 재현된 결정은 `UNEXPLAINED`), 그 밖은 `UNEXPLAINED` |
| 사전 검증 | 잠금 파일이 없거나, 커밋되지 않았거나, 변경되었거나, params가 grid 밖이면 실행 거부. 정적 검사로 `allow_holdout=True`를 쓰는 곳이 `backtest/holdout.py`와 `paper/runner.py`뿐인지 확인 |
| 텔레그램 | 가짜 전송기로 메시지 포맷 확인, 토큰이 없으면 건너뜀, 재시도, 미전송 이벤트 재시도. 실제 네트워크 호출 없음 |
| 일일 요약 시각 | 뉴욕 09:00 이후 첫 실행에만 보내는지, 서머타임 전환일, 하루 1회 |
| 실행 공백 | 3시간 초과면 경고 |

### 7.2 통합 테스트 (합성 데이터로 시간 흐름 재현)
- 합성 1시간봉과 테스트용 `holdout.lock`을 만든다. `paper run`을 시계를 1시간씩 옮겨 가며 N회 실행한다.
- **최종 기록 일치**: 마지막 `ledger.json`의 거래와 결정이 한 번에 처음부터 돌린 결과와 같아야 한다.
- **실행 누락 내성**: 중간 실행 일부를 건너뛰어도 최종 기록이 같아야 한다.
- **알림 중복 없음**: 모든 이벤트가 정확히 한 번씩 알려져야 한다.
- **데이터 수정 감지**: 과거 봉 1개를 수정한 시나리오에서 `DATA_REVISION` 경고가 나와야 한다.

### 7.3 배포 전 확인
1. 로컬에서 실제 데이터로 `ewbot paper run`을 1회 실행한다.
   - 기준 지문이 `64e628a` 재계산 값과 같은지 확인한다.
   - 홀드아웃 데이터 해시가 잠금 파일과 같은지 확인한다.
   - 홀드아웃 이후 현재까지의 표본 외 거래 목록을 확인한다.
2. Actions에서 수동 실행을 1회 한다. `paper` 브랜치에 커밋이 생기는지, 텔레그램이 도착하는지(토큰 등록 시) 확인한다.
3. 24시간 예약 실행을 관찰한다. 실행 커버리지, 실행 공백 경고 여부, 일일 요약 수신을 확인한다.

## 8. 알려진 한계
- **실행 환경 고정**: 모의매매 운영 중에는 `uv.lock`, Python 버전, 실행기 이미지(`ubuntu-24.04`)를 바꾸지 않는다. 전략 지문 대상 파일은 PR·`master` 푸시마다 CI가 지문 고정값과 대조한다.
- **되돌림 불가**: 전략 지문 대상 파일을 한 번이라도 바꾸면, 원래대로 되돌려도 홀드아웃 36건은 다시 합산되지 않는다(엄격 정책).
- **예약 실행 지연·누락**: 결과에는 영향이 없다(재계산). 다만 알림이 수 분에서 수십 분 늦을 수 있다.
- **50건 도달 시점**: 연 약 10~13건이라 남은 14건을 채우는 데 1~1.5년이 걸릴 것으로 예상한다.
- **엄격 지문 정책의 대가**: 전략 영향 파일은 사실상 동결된다. 버그를 발견해 고치면 카운터가 리셋된다. 홀드아웃 36건도 더 이상 합산할 수 없고, 새 구간에서 50건을 다시 모아야 한다.
- **Actions 중단 감지**: Actions 자체가 멈추면 실행 안에서는 알 수 없다(§6.4).
- **실시간성**: 체결은 봉 시가 기준 시뮬레이션이다. 실제 호가, 슬리피지, 부분 체결은 실거래 단계에서 검증한다.
